# Apps

Sumi is a shell. Every page a person opens (chat, tasks, canvas, terminal, a browser page) is an app: runnable alone in a browser, drawn in a sandboxed frame, and speaking to Sumi only through `@sumi/contract`. The design behind this page, with the prior art it rests on, is https://claude.ai/artifact/Y1WxRtpr7h227vGYjpTEY9; where they disagree, this page wins.

> Status: chat, tasks, terminal and browser-page are apps in this monorepo; canvas and the browser are still drawn by the studio. Everything marked **planned** is not built yet.

## Built-in apps are part of the project

**A built-in app is a folder of this monorepo, never installed.** `apps/<id>/` holds its frontend and `sumi-app.json`, its manifest; its domain modules stay in the shell's `packages/domain/*`. Today: `apps/chat`, `apps/tasks`, `apps/terminal`, `apps/browser-page` (copied from the former `sumi-*` repositories, which are no longer read). An app's workspace dependencies are the shell's own packages (`@sumi/contract` is `packages/shared/contract`), and `vite build` in its folder writes `apps/<id>/dist`.

**One registry, generated.** `widgetarium generate` (`packages/shared/cli/src/apps-registry.ts`) reads every `apps/*/sumi-app.json` and writes `packages/shared/app-registry/generated/`: `registered-apps.ts` (id, name, ui, build folder), `registered-apps.json` (id and build folder, read by Rust) and `app-modules.ts` (the runnable modules the apps bring: a module name with a `packages/domain|state/<name>/module.ts` exporting `<Name>Module`, today `TasksModule` and `TerminalModule`). Nothing hand-maintains a list of apps. A manifest that does not parse, names another id than its folder, or asks a contract range Sumi does not speak (`contractRefusal`) fails generation; `generate --check` fails on a stale registry.

**Registered at start.** The core registers `APP_MODULES` beside its own modules (`start-core.ts` in Tauri, `startCoreInProcess` in a browser), and the shell reads `REGISTERED_APPS` for faces, links and frames (`@widgetarium/app-registry`); no action of the person is involved.

**What stays in the shell:** Places (tabs, address, history, title, favicon), workspaces, the page frame, the event bus, the registry, and every native power: the Rust core, the terminal pty, browser webviews, the agent runner, the file store. **Only the shell imports Tauri.** An app reaches a native power through a request of a shell module `@sumi/contract` lists (`file-system`, `terminal`), never by importing `@tauri-apps/api`.

## The contract

`@sumi/contract` is `packages/shared/contract` in the shell. It holds these and nothing else:

| File                     | Holds                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| `index.ts`, `generated/` | written by `widgetarium generate` from `sumi-contract.json`: each listed module's generated contract     |
| `manifest.ts`            | `AppManifestSchema`, `defineApp`, `APP_MANIFEST_FILE` (`sumi-app.json`)                                  |
| `version.ts`             | `CONTRACT_VERSION`, `CONTRACT_RANGE`, `contractRefusal(appRange, sumiVersion)`                           |
| `link-catcher.ts`        | `catchLinks({ sumi, tabId })`: every app's one link handler (see Links under The contract)               |
| `theme-wearer.ts`        | `wearSumiTheme({ sumi, transport })`: puts `dark` and `theme-dark` on the frame's root from `ThemeQuery` |

`sumi-contract.json` lists the shell modules an app may call: `["file-system", "terminal", "places", "web-page", "assistant", "appearance"]`. The generator copies each module's `"."` contract (requests and schemas, no handler, imports only `zod` and `@widgetarium/data-framework`) into `generated/<module>.ts`, so the built package is self-contained: its runtime peers are `@widgetarium/core` and `zod`. `npm run generate -- --check` fails on a stale copy. The transport is the framework's ([requests.md](requests.md#the-frame-transport)); an app writes:

```ts skip-check
const sumi = messagePortTransport(portFromParent());
const tasks = app().imports(FileSystemModule.over(sumi), PlacesModule.over(sumi)).start();
```

There is no message vocabulary between Sumi and an app: everything an app asks is a command or a query of a listed module.

| Module        | Requests                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file-system` | `ReadFileQuery`, `ReadFolderQuery`, `FileInfoQuery` (answers a missing path), `WriteFileCommand`, `AppendFileCommand`, `MakeFolderCommand`, `RemoveCommand`, `RenameCommand`, `CopyCommand`                                                                                                                                                                                                                                                                                                                                                                                |
| `terminal`    | `SendTerminalCommand { line }` (typed into the app's own shell session, then Enter; the line is never altered), `TerminalOutputQuery` (the last 256 KiB, running, exit code)                                                                                                                                                                                                                                                                                                                                                                                               |
| `places`      | the whole module is imported; `AppCallersGuard` lets an app call only `OpenTabCommand`, `RecordAppPageCommand { id, address?, how?: push \| replace, title?, favicon?, actions? }`, `AppTabQuery`, `OpenLinkCommand { from, href, inNewTab }` and `TakeActionPressCommand { id, press }`, `OwnsAppTabGuard` and `OwnsLinkingTabGuard` only for a tab that holds that app                                                                                                                                                                                                   |
| `web-page`    | `OpenWebPageCommand { tab, url }` (http and https only; the page opens in the app's own browser profile `app-<id>`), `PlaceWebPageCommand { tab, area: { x, y, width, height } \| null }` (the frame's own CSS pixels, each 0 to 16384, clamped to the frame; `null` hides), `GoBackWebPageCommand`, `GoForwardWebPageCommand`, `ReloadWebPageCommand`, `CloseWebPageCommand` `{ tab }`, `WebPageQuery { tab }` → `{ url, title, isLoading, canGoBack, canGoForward } \| null` (the url without its `#fragment`)                                                           |
| `assistant`   | only for the `chat` app in a chat tab; `AssistantCallersGuard` lets an app call only its own chat's conversation (chat, turns, sending, compacting, clearing, the draft and its attachments, slash commands), read `agent-setup`, `claude-options` and `working-folders`, and choose the provider, the model, its options and the working folder (`choose-provider`, `open-providers`, `choose-claude-option`, `choose-claude-model`, `choose-working-folder`, `pick-working-folder`): the picker is drawn inside the chat; file drags and folder lending stay the shell's |

**Paths.** A relative path resolves inside the app's own folder in the calling window's workspace, `<appData>/app-data/<workspace id>/<app id>/` (`placedPathOf`); the workspace comes from the core's scope, so an app never names it; a path climbing out of it is refused; an absolute path is taken as given for now. **Watching** is not a request: every write invalidates the three read queries, which reach the frame through the transport's `changes` (TODO: invalidating only the written path, and changes made outside Sumi).

**Permissions are later; the seams are there.** Each module runs `AuthenticatedGuard`, then `FileAccessGuard` / `TerminalAccessGuard`, which allow every app everything today, then a middleware logging app, request and paths (`[file-system] app notes → file-system/write-file ["tasks.json"]`). Refusing `rm` or limiting folders is one guard.

**Where the work happens.** In Tauri the core window serves both modules: `TauriFilesGateway` calls the Rust plugin `files` (`src-tauri/src/files.rs`, studio windows only), `TauriTerminalSessionsGateway` opens one pty per app through `terminal.rs`, whose end now carries the exit code. The browser studio serves memory gateways; `NodeFilesGateway` and `NodeTerminalSessionsGateway` serve the end-to-end test.

**Routes: who serves a frame.** The relay is built per frame mount from `routesFor({ app, tabId })` (`frameRoutesOf`, `apps/studio/src/tabs/frame-routes.ts`), each route a module contract and the transport serving it; a call goes to its module's route, a change reaches the frame only for that route's queries, and a `web-page` change only for the frame's own tab; routes sharing a transport are heard through it once. `file-system`, `terminal` and `places` go to the core. `web-page` and `assistant` are served inside the studio window, `server().modules(...).listen(localTransport())` with `AppCallerAuthenticate`:

- **`web-page`** owns no page itself. `AppOwnsTabGuard` asks Places, through the studio app's `AppTabQuery`, whether the tab holds the calling app. In Tauri the studio lends `nativeWebPagesOver(studioApp)`: it sends the browser module's `OpenPageCommand`, `OpenAddressCommand`, `GoBackCommand`, `GoForwardCommand`, `ReloadPageCommand`, `ClosePageCommand` and `BrowserTabsQuery` keyed by the app's tab id, and places a hole element over the frame at the asked area with `AttachPagesCommand { host, heldTabId: tab }`, so the browser module stays the one owner of native pages. A hole is kept only after the attach succeeds, hides while its frame is detached or has no size, and a frame unmounting closes its tab's page. The server is held while any frame uses it and stopped after the last. The browser studio and the tests use `MemoryWebPagesGateway`, a fake that keeps history and titles a page by its host. A page change re-reads `WebPageQuery` through `WebPagesChangedEvent` and `RereadWebPageSubscriber`.
- **`assistant`** is `.on(Anywhere)`: the studio still runs it in its chat apps, and `frameChatServersOf` (a `ServerLeases`) serves it for frames, one server per chat id over `portForChat`, started for the first frame and stopped after the last. A frame gets the route only when its app is `chat` and `AppTabQuery` answers a `chatId` for its tab, which Places sets to the tab's own id for a chat tab and `null` for any other, so an address an app records never names a chat.

**The tab and its history.** The shell opens the frame at `<pageUrl>#sumi-tab=<tab id>`; the app reads `AppTabQuery { id }` → `{ id, app, address, title, chatId, canGoBack, canGoForward }`, shows that address, and re-reads it on every change. Places owns the tab's history (`KeptTab.history`, 50 steps each way): when the person moves to another page the app records it with `RecordAppPageCommand { how: "push" }`, which makes a step back and clears forward; a change that is not a page (a filter, the board or list switch) records nothing, or `how: "replace"`. A push without a title clears the old one until the app reports the new. Back and forward are the shell's: `GoBackInTabCommand` and `GoForwardInTabCommand` (the studio only) move the address, and the app re-reads it, the same way it starts.

**The header is the shell's.** An app draws only its body: no plate, no header row of its own. For an app's tab (the chat excepted, whose plate has its own header) the studio draws `AppHeader` (`apps/studio/src/features/app-frame/ui/app-header`) into the plate header the built-in pages use: back and forward from `canGoBack`/`canGoForward`, the crumb "App / page title" and the app's actions. Every crumb, the browser's, an app's and the chat's ("Workspace / chat"), is one button (`PlateCrumb`, the chat's `ChatLinkCrumb`) with one hover over all its words and no part of its own: it opens the command menu at this tab filled with the tab's deep link (`sumi://tasks/T-1`, `sumi://chat/<id>`; a web page shows its plain address), and a typed `sumi://` link opens through app-host's `OpenLinkCommand`.

**Header actions.** An app's buttons are data: it records them with `RecordAppPageCommand { actions: [{ id, label, icon, isOff?, isBusy? }] }` (at most 6; a record without `actions` keeps them), and `AppActions` draws them in the header's `controls` slot. A press is the shell's: `PressAppActionCommand { tab, action }` (refused to apps; refused for an action the tab does not show or that is off) keeps it in `PlacedTabs.pendingPresses`, `AppTabQuery` answers the tab's `presses`, and the app takes each once with `TakeActionPressCommand`, the same shape as asked links. An app wires both through `startHeaderActions({ sumi, transport, tabId })` from the contract: `show(actions)` records them with a `run` each, and every press taken runs its action. View controls (filters, a mode switch, search) are not actions: they stay in the app's body.

**Links.** An app writes plain anchors: `<a href="/T-2">` (a page of the same app), `<a href="sumi://tasks/T-1">`, `<a href="https://…">`, with `target="_blank"`, cmd, ctrl or shift, or the middle button for a new tab. `catchLinks` from the contract hears every press on the document in the capture phase, stops the frame from navigating, and sends Places' `OpenLinkCommand { from: its own tab, href, inNewTab }`; the app never knows its window. **Routing lives in Places** (`linkRouteOf`, `features/tab-facts/lib/link-routes.ts`), because Places owns tabs, addresses and history: `/<page>` and `sumi://<this app>/<page>` in the same tab push that tab's address; anything else (a new tab, another app, a web page) is recorded as an asked link, `{ id, from, href, inNewTab }` in `PlacedTabs.askedLinks`, a scheme Places cannot open is refused. Showing a tab still needs the studio's screen (panes, browser pages, the shown view: app-host's `settleAsked`), so the studio window holding the `from` tab reads `AskedLinksQuery`, takes each link once with `TakeAskedLinkCommand` and opens it with app-host's `OpenLinkCommand` (TRADE-OFF: until app-host's showing moves into Places, the last step of a link runs in the studio). There an `http(s)` link opens a shown `browser-page` tab at that address whenever `browser-page` is registered, else the built-in browser; `sumi://<app id>/<page>` opens any app Sumi knows, drawn by the shell or registered (`linkTargetOf` in `packages/shared/core/src/engine/sumi-link.ts`), and `sumi://chat/<id>`, `sumi://tab/<id>`, `sumi://task/<id>` and `sumi://app/<id>` still read.

**Theme.** Sumi's theme has one owner, `@widgetarium/appearance` (`packages/state/appearance`): `ThemeQuery` → `{ scheme: light | dark, choice: system | light | dark }` and `ChooseThemeCommand` (refused to an app by `StudioCallerGuard`). The studio window serves it once on a local transport (`startStudioAppearance`), wears it on its own document, and routes frames to it; the system scheme reaches the module as the `SystemScheme` host object, and a change of either re-reads `ThemeQuery` everywhere (`ThemeChangedEvent`). An app calls `wearSumiTheme`; nothing in an app reads `prefers-color-scheme`. TODO: the choice is kept in memory, not in the workspace settings.

**Versioning: one number, additive only.** Within a major the contract only grows: a new module, request or optional field; nothing is renamed, removed or narrowed. An app's manifest names the range it was built for, `contract: "^0.3.2"`; `contractRefusal` answers it against what Sumi speaks. Before 1.0 a minor is a breaking line. 0.3 replaced the 0.2 message protocol; 0.3.1 added `web-page` and `assistant`; 0.3.2 added Places' history and links, `appearance`, `catchLinks` and `wearSumiTheme`; 0.3.3 added `questions`, the agent's needed and optional questions a chat draws above its input. 0.3.4 added the assistant's message queue: `queued` on the session and the chat, `change-queue`, `send-text`, `replaces` on `send-message`, and `questions/ready-answers`. 0.3.5 added header actions: `actions` on `RecordAppPageCommand`, `actions` and `presses` on `AppTabQuery`, `TakeActionPressCommand` and `startHeaderActions`, and opened the provider, model and folder choices to the chat app.

**The gate is generation.** `widgetarium generate` refuses an `apps/*` manifest whose `contract` range Sumi does not satisfy, so no registered app speaks another contract.

**An app cannot pretend to be another app.** The shell decides who a frame is when it creates it: `servePortHandovers` answers only a handover wanted by that frame, and the relay stamps the app id the shell opened there; nothing the app sends names its caller.

**A failure reaches both people.** A refused or failed call answers the app with its code and reason; the full error goes to the core's `reportFailure`.

`npm run test:sumi-contract` runs the version gate, the manifest, a call over a `MessagePort`, every module over memory gateways or a fake `AssistantPort`, the assistant allow-list and the chat servers' lifetime; `npm run test:contract-frame` runs a tiny app in a real sandboxed iframe in headless Chrome that writes and reads a file and types a line into a real `/bin/sh` (the core, a node server), then opens a web page and chats through routes served in the shell page by `frameRoutesOf` (the memory fake browser and an echoing fake port: no native page and no real agent).

## Modules and the bus

An app's manifest lists its modules: `modules: [{ name, runs: "page" | "background" }]`. The app's code never names the shell's modules; it sends contract messages, and the shell wires each module to the one bus. Background modules run in the shell's hidden core window, all in one for now (**planned**; splitting them into separate processes is a later decision).

**MCP is a transport** (**planned**). A framework server already listens on several transports (`server().modules(...).listen(transport)`, [requests.md](requests.md)); `mcpTransport()` is one more, so every public request of a module becomes an MCP tool with no MCP code in the app. The shell serves one MCP endpoint for any provider (Claude Code, Codex…), tools named by app (`tasks.create_task`), each app switchable on and off. A manifest says `mcp: true`; there is no second registry for MCP.

The chat's sub-tabs under a chat stay drawn by the shell's own code until apps can contribute UI.

## Pages of the apps

**There is nothing to install, update or roll back.** The app installer, its Rust plugin, `store.json`, the version folders under `<appData>/apps/`, releases (`sumi-release.json`) and the Install and Update rows are gone; an app changes when its folder changes and is rebuilt.

**Serving.** In Tauri the scheme `sumi-app://<id>/<file>` (`apps/host-tauri/src-tauri/src/app_pages/`) serves `<file>` from the build folder `registered-apps.json` names for `<id>` (`apps/<id>/dist`), resolved against the monorepo checkout, with the app's frame policy (`app_pages/frame-policy.txt`) on every file, to studio windows only; a path climbing out of the build, a symlink or an unregistered id is 404. TODO: a release bundle carries no app builds yet, so a packaged Sumi draws no app, and web links, which open in `browser-page`, draw nothing. `cargo test --test app_pages_rules` pins it.

**A tab of an app.** Places keeps any app id matching `^[a-z][a-z0-9-]*$` (`AppKindSchema`). The studio draws `canvas` and `browser` itself and every other id with `AppPage` (`apps/studio/src/features/app-frame`): a registered id draws its frame, any other a missing-app note naming it. The chat plate always draws the `chat` app at the chat tab's id; the chat's sub-tabs stay the shell's, and `AppTabQuery` answers a chat tab's address as its chat id, whatever an app records. A chat tab keeps the title of its chat: `RecordAppPageCommand` refuses a tab that does not run in a page.

The frame is `<iframe sandbox="allow-scripts allow-forms">` (`APP_FRAME_SANDBOX`) at the app's page url, `sumi-app://<id>/<ui>` (`sumiAppPageUrlOf`; a test lends its own through `StudioStart.appPageUrlOf`), with `#sumi-tab=<tab id>` and served by the relay ([The contract](#the-contract)): the app records its address, title and favicon with Places' `RecordAppPageCommand`, whose `AppPageSchema` bounds the title (200), the address (2 048) and the favicon (`data:image/…` up to 64 KiB or `sumi-app://<the same id>/…`; another app's is dropped and reported), and reads where Places moved the tab with `AppTabQuery`. An app follows a link through Places (see Links under The contract), never `OpenTabCommand`, whose `at` (window, view, screen) it cannot know. The command menu lists the registered page apps by manifest name; links and the menu read app-host's `AppFacesQuery`, the shell's faces with the registered apps over them.

**What keeps a frame from the IPC.** The frame runs in an opaque origin (no `allow-same-origin`), so `parent.__TAURI_INTERNALS__` and `top.__TAURI_INTERNALS__` throw and it has none of its own; the scheme's `Content-Security-Policy` (`app_pages/frame-policy.txt`, the one owner of that line) names neither `ipc:` nor `http://ipc.localhost` in `connect-src`. `npm run test:app-frame-sandbox` proves both in headless Chrome, the template's `sumi-app://{app}` filled and mapped to the test server's origin. Tauri treats any registered custom scheme as local (`tauri-2.12.4/src/webview/mod.rs:1978-1985`), so what keeps a frame out of IPC is the invoke key only the main frame's scripts hold (`webview/mod.rs:2010-2026`, `manager/webview.rs:161-166`) and the `null` Origin refused on the `ipc://` route (`ipc/protocol.rs:488-495`). Not verified in a real WKWebView.

`npm run test:sumi-apps [tasks terminal browser-page chat]` builds each app in its folder, serves the builds the way the scheme does, starts the studio with no action and drives every app in Chrome: the registry matches `apps/*`, the menu offers no Install, each frame draws after a reload, and the chat matches the built-in chat of tag `builtin-apps-before-removal` in light and dark.

## The Tasks app

`apps/tasks` runs no tasks module of its own: its page imports `TasksModule` over the frame, and `frameRoutesOf` routes it to the core window, the one place `@widgetarium/tasks` runs. The core lends the module a `BoardFile` (`apps/host-tauri/src/core-link/tasks-board-file.ts`) whose `read` and `write` are `ReadFileQuery` and `WriteFileCommand` sent as app `tasks`, so the board lives in `app-data/<workspace>/tasks/tasks.json` under the plain relative path `tasks.json`. `FileTasksGateway` keeps `{ rev, board }` in it (TRADE-OFF: the rev is read, then written; FileSystem has no compare-and-write yet, and the core is its one writer). Agent tools, chat task lines and the page all read that one board.
