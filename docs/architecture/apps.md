# Apps

Sumi is a shell. Every page a person opens (chat, tasks, canvas, terminal, a browser page) is an app: its own repository, runnable alone in a browser, plugged into Sumi through a registry, and speaking to Sumi only through `@sumi/contract`. The design behind this page, with the prior art it rests on, is https://claude.ai/artifact/Y1WxRtpr7h227vGYjpTEY9; where they disagree, this page wins.

> Status: the repositories and `@sumi/contract` 0.3 exist. Everything marked **planned** is not built yet.

## The repositories

```
~/Projects/Sumi/                  not a repository: the folder that holds them
  pnpm-workspace.yaml             dev only: links every repository's packages by name
  sumi/                           this repository: the shell (a link to it)
  packages/                       built tarballs apps install outside the workspace (@sumi/contract)
  sumi-framework/                 planned: core (requests, modules, transports), cli, vite, eslint-plugin
  sumi-kit/                       planned: the reusable UI every app imports
  sumi-tasks/  sumi-canvas/  sumi-chat/  sumi-terminal/  sumi-browser-page/
```

An app repository is a pnpm workspace: `packages/domain/*` holds its modules, `apps/*` its frontend. `sumi-app.json` at its root is its manifest.

**What stays in the shell:** Places (tabs, address, history, title, favicon), workspaces, the page frame, the event bus, the app installer (install, update, roll back), and every native power: the Rust core, the terminal pty, browser webviews, the agent runner, the file store. **Only the shell imports Tauri.** An app reaches a native power through a request of a shell module `@sumi/contract` lists (`file-system`, `terminal`), never by importing `@tauri-apps/api`.

**Developing across repositories needs no publish.** `pnpm install` in `~/Projects/Sumi` links `@sumi/contract` from the shell's `packages/shared/contract` (and later the framework and kit) into every repository that depends on it, by package name; `npm pack` of the built contract into `~/Projects/Sumi/packages/` is the self-contained copy an app outside the workspace installs; an edit in one shows in the next run of another. npm is for releases. The shell joins the dev workspace when it moves from npm workspaces to pnpm (**planned**, with the framework extraction).

## The contract

`@sumi/contract` is `packages/shared/contract` in the shell. It holds these and nothing else:

| File                     | Holds                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| `index.ts`, `generated/` | written by `widgetarium generate` from `sumi-contract.json`: each listed module's generated contract     |
| `manifest.ts`            | `AppManifestSchema`, `defineApp`, `APP_MANIFEST_FILE` (`sumi-app.json`)                                  |
| `version.ts`             | `CONTRACT_VERSION`, `CONTRACT_RANGE`, `contractRefusal(appRange, sumiVersion)`                           |
| `link-catcher.ts`        | `catchLinks({ sumi, tabId })`: every app's one link handler (see Links under The contract)               |
| `theme-wearer.ts`        | `wearSumiTheme({ sumi, transport })`: puts `dark` and `theme-dark` on the frame's root from `ThemeQuery` |

`sumi-contract.json` lists the shell modules an app may call: `["file-system", "terminal", "places", "web-page", "assistant", "appearance"]`. The generator copies each module's `"."` contract (requests and schemas, no handler, imports only `zod` and `@widgetarium/core/requests`) into `generated/<module>.ts`, so the built package is self-contained: its runtime peers are `@widgetarium/core` and `zod`. `npm run generate -- --check` fails on a stale copy. The transport is the framework's ([requests.md](requests.md#the-frame-transport)); an app writes:

```ts skip-check
const sumi = messagePortTransport(portFromParent());
const tasks = app().imports(FileSystemModule.over(sumi), PlacesModule.over(sumi)).start();
```

There is no message vocabulary between Sumi and an app: everything an app asks is a command or a query of a listed module.

| Module        | Requests                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file-system` | `ReadFileQuery`, `ReadFolderQuery`, `FileInfoQuery` (answers a missing path), `WriteFileCommand`, `AppendFileCommand`, `MakeFolderCommand`, `RemoveCommand`, `RenameCommand`, `CopyCommand`                                                                                                                                                                                                                                                                                                                      |
| `terminal`    | `SendTerminalCommand { line }` (typed into the app's own shell session, then Enter; the line is never altered), `TerminalOutputQuery` (the last 256 KiB, running, exit code)                                                                                                                                                                                                                                                                                                                                     |
| `places`      | the whole module is imported; `AppCallersGuard` lets an app call only `OpenTabCommand`, `RecordAppPageCommand { id, address?, how?: push \| replace, title?, favicon? }`, `AppTabQuery` and `OpenLinkCommand { from, href, inNewTab }`, `OwnsAppTabGuard` and `OwnsLinkingTabGuard` only for a tab that holds that app                                                                                                                                                                                           |
| `web-page`    | `OpenWebPageCommand { tab, url }` (http and https only; the page opens in the app's own browser profile `app-<id>`), `PlaceWebPageCommand { tab, area: { x, y, width, height } \| null }` (the frame's own CSS pixels, each 0 to 16384, clamped to the frame; `null` hides), `GoBackWebPageCommand`, `GoForwardWebPageCommand`, `ReloadWebPageCommand`, `CloseWebPageCommand` `{ tab }`, `WebPageQuery { tab }` → `{ url, title, isLoading, canGoBack, canGoForward } \| null` (the url without its `#fragment`) |
| `assistant`   | only for the `chat` app in a chat tab; `AssistantCallersGuard` lets an app call only its own chat's conversation (chat, turns, sending, compacting, clearing, the draft and its attachments, slash commands) and read `agent-setup`, `claude-options` and `working-folders`; choosing a provider, a model or a folder, file drags and folder lending stay the shell's                                                                                                                                            |

**Paths.** A relative path resolves inside the app's own folder, `<appData>/app-data/<app id>/` (`placedPathOf`); a path climbing out of it is refused; an absolute path is taken as given for now. **Watching** is not a request: every write invalidates the three read queries, which reach the frame through the transport's `changes` (TODO: invalidating only the written path, and changes made outside Sumi).

**Permissions are later; the seams are there.** Each module runs `AuthenticatedGuard`, then `FileAccessGuard` / `TerminalAccessGuard`, which allow every app everything today, then a middleware logging app, request and paths (`[file-system] app notes → file-system/write-file ["tasks.json"]`). Refusing `rm` or limiting folders is one guard.

**Where the work happens.** In Tauri the core window serves both modules: `TauriFilesGateway` calls the Rust plugin `files` (`src-tauri/src/files.rs`, studio windows only), `TauriTerminalSessionsGateway` opens one pty per app through `terminal.rs`, whose end now carries the exit code. The browser studio serves memory gateways; `NodeFilesGateway` and `NodeTerminalSessionsGateway` serve the end-to-end test.

**Routes: who serves a frame.** The relay is built per frame mount from `routesFor({ app, tabId })` (`frameRoutesOf`, `apps/studio/src/tabs/frame-routes.ts`), each route a module contract and the transport serving it; a call goes to its module's route, a change reaches the frame only for that route's queries, and a `web-page` change only for the frame's own tab; routes sharing a transport are heard through it once. `file-system`, `terminal` and `places` go to the core. `web-page` and `assistant` are served inside the studio window, `server().modules(...).listen(localTransport())` with `AppCallerAuthenticate`:

- **`web-page`** owns no page itself. `AppOwnsTabGuard` asks Places, through the studio app's `AppTabQuery`, whether the tab holds the calling app. In Tauri the studio lends `nativeWebPagesOver(studioApp)`: it sends the browser module's `OpenPageCommand`, `OpenAddressCommand`, `GoBackCommand`, `GoForwardCommand`, `ReloadPageCommand`, `ClosePageCommand` and `BrowserTabsQuery` keyed by the app's tab id, and places a hole element over the frame at the asked area with `AttachPagesCommand { host, heldTabId: tab }`, so the browser module stays the one owner of native pages. A hole is kept only after the attach succeeds, hides while its frame is detached or has no size, and a frame unmounting closes its tab's page. The server is held while any frame uses it and stopped after the last. The browser studio and the tests use `MemoryWebPagesGateway`, a fake that keeps history and titles a page by its host. A page change re-reads `WebPageQuery` through `WebPagesChangedEvent` and `RereadWebPageSubscriber`.
- **`assistant`** is `.on(Anywhere)`: the studio still runs it in its chat apps, and `frameChatServersOf` (a `ServerLeases`) serves it for frames, one server per chat id over `portForChat`, started for the first frame and stopped after the last. A frame gets the route only when its app is `chat` and `AppTabQuery` answers a `chatId` for its tab, which Places sets to the tab's own id for a chat tab and `null` for any other, so an address an app records never names a chat.

**The tab and its history.** The shell opens the frame at `<pageUrl>#sumi-tab=<tab id>`; the app reads `AppTabQuery { id }` → `{ id, app, address, title, chatId, canGoBack, canGoForward }`, shows that address, and re-reads it on every change. Places owns the tab's history (`KeptTab.history`, 50 steps each way): when the person moves to another page the app records it with `RecordAppPageCommand { how: "push" }`, which makes a step back and clears forward; a change that is not a page (a filter, the board or list switch) records nothing, or `how: "replace"`. A push without a title clears the old one until the app reports the new. Back and forward are the shell's: `GoBackInTabCommand` and `GoForwardInTabCommand` (the studio only) move the address, and the app re-reads it, the same way it starts.

**The header is the shell's.** An app draws only its body. For an installed app's tab (the chat excepted, whose plate has its own header) the studio draws `AppHeader` (`apps/studio/src/features/app-frame/ui/app-header`) into the plate header the built-in pages use: back and forward from `canGoBack`/`canGoForward`, and the crumb "App / page title" (`AppCrumb`): the app's name from its manifest presses the tab home (a push of `""`), the page title opens the command menu at this tab, the address field.

**Links.** An app writes plain anchors: `<a href="/T-2">` (a page of the same app), `<a href="sumi://tasks/T-1">`, `<a href="https://…">`, with `target="_blank"`, cmd, ctrl or shift, or the middle button for a new tab. `catchLinks` from the contract hears every press on the document in the capture phase, stops the frame from navigating, and sends Places' `OpenLinkCommand { from: its own tab, href, inNewTab }`; the app never knows its window. **Routing lives in Places** (`linkRouteOf`, `features/tab-facts/lib/link-routes.ts`), because Places owns tabs, addresses and history: `/<page>` and `sumi://<this app>/<page>` in the same tab push that tab's address; anything else (a new tab, another app, a web page) is recorded as an asked link, `{ id, from, href, inNewTab }` in `PlacedTabs.askedLinks`, a scheme Places cannot open is refused. Showing a tab still needs the studio's screen (panes, browser pages, the shown view: app-host's `settleAsked`), so the studio window holding the `from` tab reads `AskedLinksQuery`, takes each link once with `TakeAskedLinkCommand` and opens it with app-host's `OpenLinkCommand` (TRADE-OFF: until app-host's showing moves into Places, the last step of a link runs in the studio). There an `http(s)` link opens a shown `browser-page` tab at that address whenever Sumi knows the app (installed, or listed in the registry, which draws its Install), else the built-in browser; `sumi://<app id>/<page>` opens any app the registry knows, built-in, installed or listed (`linkTargetOf` in `packages/shared/core/src/engine/sumi-link.ts`), and `sumi://chat/<id>`, `sumi://tab/<id>`, `sumi://task/<id>` and `sumi://app/<id>` still read.

**Theme.** Sumi's theme has one owner, `@widgetarium/appearance` (`packages/state/appearance`): `ThemeQuery` → `{ scheme: light | dark, choice: system | light | dark }` and `ChooseThemeCommand` (refused to an app by `StudioCallerGuard`). The studio window serves it once on a local transport (`startStudioAppearance`), wears it on its own document, and routes frames to it; the system scheme reaches the module as the `SystemScheme` host object, and a change of either re-reads `ThemeQuery` everywhere (`ThemeChangedEvent`). An app calls `wearSumiTheme`; nothing in an app reads `prefers-color-scheme`. TODO: the choice is kept in memory, not in the workspace settings.

**Versioning: one number, additive only.** Within a major the contract only grows: a new module, request or optional field; nothing is renamed, removed or narrowed. An app's manifest names the range it was built for, `contract: "^0.3.2"`; `contractRefusal` answers it against what Sumi speaks. Before 1.0 a minor is a breaking line. 0.3 replaced the 0.2 message protocol; 0.3.1 added `web-page` and `assistant`; 0.3.2 added Places' history and links, `appearance`, `catchLinks` and `wearSumiTheme`.

**Two gates.** Before install and on an update check, the app installer refuses a release whose `contract` range Sumi does not satisfy (`gatedManifestOf` in `packages/state/app-installer`). TODO: a runtime check for a dev server, which never passed the install gate.

**An app cannot pretend to be another app.** The shell decides who a frame is when it creates it: `servePortHandovers` answers only a handover wanted by that frame, and the relay stamps the app id the shell opened there; nothing the app sends names its caller.

**A failure reaches both people.** A refused or failed call answers the app with its code and reason; the full error goes to the core's `reportFailure`.

`npm run test:sumi-contract` runs the version gate, the manifest, a call over a `MessagePort`, every module over memory gateways or a fake `AssistantPort`, the assistant allow-list and the chat servers' lifetime; `npm run test:contract-frame` runs a tiny app in a real sandboxed iframe in headless Chrome that writes and reads a file and types a line into a real `/bin/sh` (the core, a node server), then opens a web page and chats through routes served in the shell page by `frameRoutesOf` (the memory fake browser and an echoing fake port: no native page and no real agent).

## Modules and the bus

An app's manifest lists its modules: `modules: [{ name, runs: "page" | "background" }]`. The app's code never names the shell's modules; it sends contract messages, and the shell wires each module to the one bus. Background modules run in the shell's hidden core window, all in one for now (**planned**; splitting them into separate processes is a later decision).

**MCP is a transport** (**planned**). A framework server already listens on several transports (`server().modules(...).listen(transport)`, [requests.md](requests.md)); `mcpTransport()` is one more, so every public request of a module becomes an MCP tool with no MCP code in the app. The shell serves one MCP endpoint for any provider (Claude Code, Codex…), tools named by app (`tasks.create_task`), each app switchable on and off. A manifest says `mcp: true`; there is no second registry for MCP.

The chat's sub-tabs under a chat stay drawn by the shell's own code until apps can contribute UI.

## Registry, install and updates

> Built: folder sources, install, the update check on a press, switch, rollback, the frame. **Planned**: GitHub sources, signatures, checks at start and every few hours, the setting that turns updates off, grants.

**The registry** is the list of apps Sumi may install: `<appData>/apps/registry.json`, `{ "apps": [{ id, source }] }`, written by the person; absent means empty. A source is a GitHub repository (`{ kind: "github", repository: "owner/sumi-tasks" }`, refused with "installing from GitHub is not built yet") or a folder on this machine holding a built release (`{ kind: "folder", path: "/Users/…/sumi-tasks/dist" }`). Its schema lives in the shell (`RegistryRowSchema`), because only the shell reads it. A registry that does not parse, or names an id twice, answers with a `problem`, never as an empty list in silence.

**A release** is a folder: `sumi-app.json`, `sumi-release.json` (`{ app, version, files: [{ path, sha256, size }] }`, every file but itself) and the files. `tools/app-release.ts <folder>` lays `sumi-release.json`; an app repository runs it after its build. `tools/fixtures/hello-app/src` is a hello app; `buildHelloReleases` in `tools/hello-app-build.ts` builds three releases of it (1.0.2 never sends `ready`) into a temp folder each time `test:app-installer` runs, so they always carry the contract range Sumi speaks.

**Sumi never runs an app from its source.** Installing reads the source's built release, checks it, and copies it into Sumi's own folder; the source folder or repository is only where a version comes from:

```
~/Library/Application Support/<Sumi app id>/apps/
  registry.json       written by the person, read only
  store.json          written only by the Rust app installer: current, previous, failed versions
  tasks/1.0.0/        immutable once written
  tasks/1.0.1/
```

The app id is `app.widgetarium.studio` today (`tauri.conf.json`); renaming it moves this folder and every workspace file, so the rename carries a migration.

**One writer.** The Rust plugin `apps` (`apps/host-tauri/src-tauri/src/app_installer/`) owns `store.json` and the version folders: `registry`, `installed`, `inspect`, `install` (checks each listed file's size and sha256, the ids and versions, copies, renames; an app's first install is current), `switch`, `fail` (a failed version never becomes current; failing the current one brings `previous` back). `@widgetarium/app-installer` (`packages/state/app-installer`) is the shell's side: `AppRegistryQuery`, `InstalledAppsQuery` (versions and the current manifest, read through `sumi-app://`), `InstallAppCommand` (registry row → `inspect` → contract gate → `install` with the `manifestSha256` inspect answered), `UpdateAppsCommand` (installs each newer release that passes the gate, then switches to it), `SwitchAppVersionCommand`, `FailAppVersionCommand`, `RetryAppVersionCommand`, each logging the `{ was, now }` Rust answers. The tauri gateway parses every answer (`.strict()`), the registry and the fetched manifest. It keeps no copy: every answer is re-read from Rust, and a Rust refusal reaches the person as a refusal (`ran: false`). Only `browser` and `app` cannot be installed (`RESERVED_IDS`, Rust `BUILT_IN_APPS`). `tasks`, `canvas`, `terminal` and `chat` can, and an installed app with a current version replaces the built-in page of its id; without one, or with every version failed, the built-in page is drawn. One decision, `appPageOf` over app-host's `AppFacesQuery` (`AppFace.isBuiltIn`), serves the tab plates and the chat plate (`ChatPage`). Every installer command emits `InstalledAppsChangedEvent`, and app-host's `RereadAppFacesSubscriber` re-reads `AppFacesQuery` and `KnownAppsQuery`, so a page switches at once. An installed `chat` runs in the chat pane at the chat tab's id; the chat's sub-tabs stay the shell's, and `AppTabQuery` answers a chat tab's address as its chat id, whatever an app records. A chat tab keeps the title of its chat: `RecordAppPageCommand` refuses a tab that does not run in a page.

**A tab of an installed app.** Places keeps any app id matching `^[a-z][a-z0-9-]*$` (`AppKindSchema`): a built-in is drawn by the shell, any other id by `InstalledAppPage` (`apps/studio/src/features/app-frame`). An id that is not installed draws a missing-app state naming it, with Install when the registry lists it. The page is `<iframe sandbox="allow-scripts allow-forms">` (`APP_FRAME_SANDBOX`) at the `pageUrl` the installer answers (`sumi-app://<id>/<version>/<ui>`), with `#sumi-tab=<tab id>` and served by the relay ([The contract](#the-contract)): the app records its address, title and favicon with Places' `RecordAppPageCommand`, whose `AppPageSchema` bounds the title (200), the address (2 048) and the favicon (`data:image/…` up to 64 KiB or `sumi-app://<the same id>/…`; another app's is dropped and reported), and reads where Places moved the tab with `AppTabQuery`. An app follows a link through Places (see Links under The contract), never `OpenTabCommand`, whose `at` (window, view, screen) it cannot know. The command menu lists installed apps by manifest name, "Install <id>" for each registry row not installed (registry ids stay known on purpose: a link to one opens the missing-app tab), and "Update apps"; links and the menu read one decision, `KnownAppsQuery`.

**Updates.** `AppFrameFleet` is the one owner of which frame runs which version. After a switch a frame reloads, shown or hidden, at the same address, because Places holds it. A frame is ready once the relay answers one of its calls ok; a version that has no ready frame in this session gets `READY_TIMEOUT_MS` (10 s), counted only while the frame is shown and the document visible; without one, the version is failed through `FailAppVersionCommand` and every frame reloads on the version now current. A refused or thrown fail is reported and forgotten, so the next failed start tries again. An app left with no current version offers "Try again" (`RetryAppVersionCommand`). `npm run test:app-installer` drives all of it in Chrome against the hello fixture over http.

**What keeps a frame from the IPC.** The frame runs in an opaque origin (no `allow-same-origin`), so `parent.__TAURI_INTERNALS__` and `top.__TAURI_INTERNALS__` throw and it has none of its own; the scheme's `Content-Security-Policy` (`app_installer/frame-policy.txt`, the one owner of that line) names neither `ipc:` nor `http://ipc.localhost` in `connect-src`. `npm run test:app-frame-sandbox` proves both in headless Chrome, the template's `sumi-app://{app}` filled and mapped to the test server's origin. Tauri treats any registered custom scheme as local (`tauri-2.12.4/src/webview/mod.rs:1978-1985`), so what keeps a frame out of IPC is the invoke key only the main frame's scripts hold (`webview/mod.rs:2010-2026`, `manager/webview.rs:161-166`) and the `null` Origin refused on the `ipc://` route (`ipc/protocol.rs:488-495`). Not verified in a real WKWebView.

## The Tasks app

`sumi-tasks` keeps its board in its own `tasks.json`: its page starts `@widgetarium/tasks` with host `file`, a `BoardFile` whose `read` and `write` are `ReadFileQuery` and `WriteFileCommand` over the frame transport. `FileTasksGateway` keeps `{ rev, board }` in the file (TRADE-OFF: the rev is read, then written; FileSystem has no compare-and-write yet). The shell's own tasks module, its `tasks.json` and the chat task lines are a separate board: the app no longer reaches them.

**The shell's own Tasks page stays** (`apps/studio/src/features/tasks`, the built-in `tasks` page) until the loaded app is proven in a real Tauri window: an installed, current `tasks` takes the tab (`AppFace.isBuiltIn`), and without one, or with every version failed, the built-in page is drawn.
